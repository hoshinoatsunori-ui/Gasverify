# GAS自動動作確認システム 要件定義・基本設計書

Nov 3, 2026 · @星野充紀

## 1. 背景・目的・スコープ

Claude Codeが生成したGASを、push・実行・結果判定・修正指示まで人手なしで回す。gasrun記事のコンセプト（AIがGAS関数を手元から実行し、戻り値と診断を受け取る）と目的が一致するため、同じ方式を採る。

**利用環境**：自宅PCを前提とする。個人Gmail（試作）と会社のWorkspace（本番運用）の2アカウントを、プロファイルで切り替えて使う（2.4節）。初版はpersonalのみを対象とし、workは会社アカウントでの確認（Q1・Q2・Q11）が済むまで対象外とする。

**背景**：現状はClaude Codeがコードを書いた後、エディタでの実行・ログ確認・結果の貼り戻しを人が行っており、AIの修正ループがそこで止まる。

**目的**

1. 生成→実行→判定→修正のループをClaude Code単独で完結させる
2. 失敗時に「コードの誤り」か「環境・準備不足」かを機械判定し、AIが正しい対処を選べるようにする
3. 業務データ・本番スクリプトへの影響と、権限の意図しない拡大を防ぐ

**スコープ**

| 区分 | 対象 |
| --- | --- |
| 対象 | 自分がオーナーのスタンドアロン／コンテナバインドGAS、関数単位の動作確認、テスト用データでの結合確認、Webアプリ（/dev）の画面確認（Claude in Chrome、10A章） |
| 対象外 | 外部からHTTPを送るWebアプリテスト、トリガー起動そのものの検証、他者所有スクリプト、本番データへの書き込み |
| 将来検討 | トリガーの模擬実行、CIからの定期実行 |

## 2. 前提条件・制約

実行基盤はApps Script APIの`scripts.run`とする。以下は公式ドキュメントに基づく制約で、設計で回避できない。

**技術制約（公式仕様）**

| No | 制約 | 設計への影響 |
| --- | --- | --- |
| T1 | スクリプトと呼び出し側は同じ「標準Cloudプロジェクト」を共有する必要があり、既定プロジェクトでは不可 | 初期設定で紐付けを行う。既定→標準への切替で再承認が発生し得る |
| T2 | CloudプロジェクトでApps Script APIを有効化する | `doctor`で検査し、終了コード2で案内 |
| T3 | 「API実行可能」としてデプロイが必要。`devMode=true`で最新保存コードを実行できるが、オーナーのみ | 検証は常にdevMode。バージョンの乱発を避ける |
| T4 | Apps Script APIはサービスアカウントでは動作しない | 本人のOAuth認証が前提。無人CIは対象外 |
| T5 | 実行時間は最大6分 | 重い処理はテストで件数を絞る引数を必須にする |
| T6 | 戻り値はプリミティブ型等のみ。Document等のApps Script固有オブジェクトは返せない | テスト関数はJSON互換の結果オブジェクトを返す規約にする（8章） |
| T7 | 失敗時は`ExecutionError`でエラー種別・メッセージ・関数名＋行番号のスタックが返る | 診断書の主情報源にする（9章） |
| T8 | `console.log`はCloud Loggingに出力され、claspの`logs`で取得できる。ただしログ閲覧のスコープとCloudプロジェクト側の設定が要り、反映まで遅れがある | Cloud Loggingは使わず、ランタイム（GV）が実行中の`console.*`を記録して実行結果と一緒に返す（F11） |

**業務環境制約（既知）**

- Webアプリのアクセス権を「全員」にできない → 外部からHTTPを送る自動テストは不採用。内部関数はscripts.run、画面は本人のログインで/devを開くClaude in Chromeで検証する（10A章）
- GASからのメールで添付送信不可 → メール送信系は本文のみを検証対象とし、送信自体はdry-run（8章）

**業務環境制約（未確認・導入可否を左右）** → 13章の確認事項Q1〜Q3

- 標準Cloudプロジェクトの作成・紐付け権限
- 独自OAuthクライアント（内部アプリ）の管理者許可
- ユーザー設定でのApps Script API有効化の可否

**2.4 利用環境（自宅PC・2アカウント）**

同じ自宅PC上で、用途の異なる2つのプロファイルを使い分ける。認証情報・スクリプトID・許可リスト・Cloudプロジェクトはプロファイルごとに完全に分ける。

| 項目 | personal（個人Gmail） | work（会社Workspace） |
| --- | --- | --- |
| 用途 | 試作・ツール自体の開発 | 業務GASの動作確認 |
| Cloudプロジェクト | 個人で作成（組織なし） | 会社の組織配下（Q1） |
| OAuth同意画面 | 外部＋テスト中。テスト中のアプリはリフレッシュトークンが7日で失効するため、週一度の再ログインが必要（Q12） | 内部（Q2） |
| 管理者の制約 | なし | 本章の業務環境制約（既知・未確認）がそのまま適用。自宅PCからの利用可否も要確認（Q11） |
| 扱うデータ | ダミーデータのみ | 業務データのテスト用コピー |

- 会社のデータ・コードを個人アカウントへ持ち出さない。personalで作った汎用部分（ツール、テスト規約、共通ラッパー）だけをworkへ持ち込む
- ローカルのリポジトリもプロファイルごとに分ける

## 3. 機能要件

必須はF01〜F06の6機能（環境診断・push・実行・テスト・判定・診断書）で、これだけで修正ループが回る。

| ID | 機能 | 内容 | 優先度 |
| --- | --- | --- | --- |
| F01 | 環境診断（doctor） | ログイン状態、標準プロジェクト紐付け、Apps Script API有効化、API実行可能デプロイ、マニフェストのスコープとトークンのスコープ差分、使用する拡張サービスのAPI有効化を検査し、不足を一覧化 | 必須 |
| F02 | push | ローカルのソースを対象スクリプトへ反映（clasp push相当）。本番スクリプトIDへのpushは拒否。push前にGAS側との差分を確認し、GAS側にしかない変更があれば止める | 必須 |
| F03 | 関数実行（run） | 関数名＋JSON引数を指定しdevModeでscripts.run。戻り値をJSONで標準出力 | 必須 |
| F04 | テスト実行（test） | 規約に沿ったテスト関数（`test_`接頭辞）を全件または指定分実行し、合否を集計 | 必須 |
| F05 | 結果判定 | 終了コード0／1／2／3で「成功／コード誤り／準備不足／実行基盤障害」を区別 | 必須 |
| F06 | 診断書 | 失敗箇所（ファイル＋行）、原因分類、次の対処、直近ログをJSON＋人向け要約で出力 | 必須 |
| F07 | 自動下準備 | 検証用スクリプトへのAPI実行可能デプロイ作成など、権限を広げない準備は自動実施して再実行。Cloud側のAPI有効化とスコープ追加は自動実施せず手順を案内（11章） | 高 |
| F08 | テスト環境管理 | テスト用スプレッドシート／フォルダを設定ファイルで定義し、実行前初期化・実行後の状態取得を行う | 高 |
| F09 | 副作用の抑止 | テスト実行時はメール送信・外部HTTP・トリガー作成をdry-run化（実行さずに記録） | 高 |
| F10 | 実行履歴 | 実行ごとの入力・結果・診断書をローカルに保存し、前回との差分を提示 | 中 |
| F11 | ログ取得 | 実行中の`console.log`/`info`/`warn`/`error`と`GV.log`をランタイムが記録し、失敗したテスト（例外で終わった場合を含む）の診断書に添付。追加のスコープは不要。テスト以外（エディタ・トリガー）の実行のログは対象外 | 中 |
| F12 | カバレッジ簡易計測 | 公開関数のうちテストが存在しない関数を列挙 | 低 |

## 4. 非機能要件

最優先は安全性（本番・権限）で、速度より優先する。数値目標は初期値で、受け入れ試験で見直す。

| ID | 区分 | 要件 |
| --- | --- | --- |
| N01 | 安全性 | 許可リストに登録したスクリプトIDのみ操作対象。未登録IDは終了コード2で拒否 |
| N02 | 安全性 | OAuthスコープはツールが自動追加しない。不足時は追加候補を提示して人の承認を待つ |
| N03 | 安全性 | 認証情報（トークン、クライアントシークレット）はリポジトリ外に保存し、.gitignoreで除外 |
| N04 | 可観測性 | すべての実行について入力・出力・所要時間・終了コードを記録 |
| N05 | 機械可読性 | 標準出力は1回の実行につき1つのJSON。人向け要約は標準エラー出力 |
| N06 | 応答性 | 1関数の実行から判定までの目標は60秒以内（GAS実行時間を除く） |
| N07 | 再現性 | 同じ入力・同じテスト環境で同じ判定になるよう、テスト前に環境を初期化 |
| N08 | 保守性 | Node.js製CLI。Claude Code以外のAIエージェントからも同じコマンドで使える |
| N09 | 動作環境 | 自宅PCを対象（OSは要確認、Q8）。Mac/Linuxは動作確認後に対象化 |

## 5. 方式検討

採用案は「案C：claspと自作CLIの併用」。push・デプロイ・ログ取得は実績のあるclaspに任せ、実行・判定・診断だけを自作する。ただしPoCとして案A（gasrun）を試用環境で先に試し、終了コード設計や診断内容を参考にする。

| 案 | 構成 | 利点 | 懸念 | 評価 |
| --- | --- | --- | --- | --- |
| A | gasrunをそのまま使う | 導入が最速。診断書・終了コード・自動下準備が既にある | 初回実行でサーバー側設定を書き換えるため、作者自身が顧客本番への使用を避けるよう注意している。配布形態・ライセンス・社内利用可否は未確認。業務端末への外部ツール導入申請が必要な可能性 | PoCで評価 |
| B | clasp runだけで構成 | 追加開発なし | 失敗時に「Unable to run」しか出ず原因が分からないと記事で指摘されている。AIが対処を選べない | 不採用 |
| C | clasp（push/deploy/logs）＋自作CLI（run/test/doctor/診断） | scripts.runの`ExecutionError`をそのまま扱え、社内制約に合わせた安全策（許可リスト、dry-run）を組み込める | 初期開発が必要（見積りは未実施） | 採用 |
| D | googleapisで全機能を自作 | 依存が最小 | push・デプロイを再実装する無駄 | 不採用 |

**実装での変更（v0.1.0）**：pushはclaspではなくApps Script API（projects.updateContent）を直接使う。claspの別ログインを不要にし、プロファイルごとの認証を1つにまとめるため。置き換え方式のため、エディタで直された分はpushで消える。v0.2.0で、push成功時に送った内容の指紋を `.gasverify/last-push/` に保存し、次のpush前にGAS側がそこから変わっていれば終了コード2で止める（GAS側の内容は `.gasverify/remote/` に保存。手元に取り込めば自動で通る）。初回は手元と違う既存ファイルがあれば止める。比較では改行コード・末尾の空白・JSONのキー順の違いは無視する（Google側の書き換えの有無は未実測）。手元の `src` を上書きしない `pull` を追加。前回pushしたままGAS側で変わっていないファイルは、手元で消しても止めない（手元での意図的な削除とみなす）。ログ取得（F11）はCloud Loggingを使わず、ランタイムが実行中の`console.*`を記録する方式で実装（T8・F11）。

## 6. システム構成

&#91;embedded content: システム構成 · 開発者PCとGoogle側\]

Claude Codeは`gasverify`だけを呼び、`gasverify`がclasp（push・ログ取得）とApps Script API（実行）を使い分ける。本番スクリプトへの経路は存在しない。ログはCloud Loggingからclasp経由で取得する。

## 7. 処理フロー

&#91;embedded content: 処理フロー · 終了コードごとの分岐\]

終了コード1だけがコード修正に戻る。2と3はコードに触れずに準備または再試行を行い、解決しなければ人に戻す（停止条件は10章）。

**verifyの内部手順**

1. 許可リストと設定を確認（外れたら終了コード2）
2. 直接呼び出しの静的検査（副作用APIの直書きを警告）
3. clasp push（検証用スクリプトへ）、関数名とファイルの対応表を保存
4. scripts.runで`gv_setup`、`test_*`、`gv_teardown`を順に実行（devMode、ランタイムの`gasverify_invoke`経由でテストモード）
5. 結果を分類し、失敗時はclaspで直近ログを取得
6. 診断書を標準出力、履歴を`.gasverify/runs`に保存して終了コードを返す

## 8. GAS側テスト規約

テスト関数は「引数なしで呼べ、決まった形のJSONを返す」ことだけを義務づける。この規約をCLAUDE.mdに書き、Claude Codeに本体と一緒に生成させる。

**8.1 スクリプトの二重化**

- 本番スクリプトとは別に「検証用スクリプト」を用意し、ツールは検証用だけを操作する（N01）
- テストコード（`test/`）は検証用へのみpushし、本番反映時は`.claspignore`で除外する
- コンテナバインドの場合は、親ファイルごとコピーした検証用を使う

**8.2 戻り値の形**

```json
{
  "name": "test_parseReceipt_fullwidthYen",
  "ok": false,
  "assertions": [
    {"label": "金額", "expected": 1200, "actual": null}
  ],
  "sideEffects": [{"type": "mail", "to": "x@example.com", "dryRun": true}],
  "logs": ["件名: 領収書"]
}
```

- `ok=false`は「コードは動いたが期待と違う」。例外は投げずに結果として返す
- 例外で終わった場合は`ExecutionError`としてCLI側で拾う（どちらも終了コード1）
- ログ（F11）：`gasverify_invoke`の実行中は`console.*`を包んで`logs`に記録する（元の出力も行う）。例外で終わった場合は戻り値を返せないため、例外のメッセージ末尾に`GV_LOGS:<JSON>`として付けて投げ直し、CLI側で取り出してメッセージから除く。件数と長さには上限を設ける（最大50件、1件500文字）

* 戻り値にBlobなどApps Script固有のオブジェクトを含めない。エラーにはならず、メソッド名と「\[native code\]」の文字列として届くため気付きにくい（実測C06）
* 公開するテスト関数の名前を`_`で終えない。外から呼ぶと403になる（実測C10）

**8.3 副作用の切り離し（F09）**

- メール送信・`UrlFetchApp`・トリガー作成は必ず共通ラッパー（例：`Effects.sendMail()`）経由で呼ぶ
- ラッパーはスクリプトプロパティ`TEST_MODE=1`のとき実行せず`sideEffects`に記録する
- 直接呼び出しは静的検査（push前のgrep）で検出し、警告とする

**8.4 テストデータ（F08）**

- テスト用スプレッドシート／フォルダのIDは設定ファイルで指定し、本体コードには書かない
- `gv_setup`／`gv_teardown`関数で初期化と後片付けを行う（末尾`_`の関数は外から呼べないため名前を変更。実測C10）
- 件数の多い処理は`limit`引数を受け付け、6分制限（T5）に収める

## 9. CLI仕様・終了コード・診断書

CLI（仮称`gasverify`）は5コマンド。AIは終了コードだけで次の行動を決め、詳細は診断書JSONを読む。

**9.1 コマンド**

| コマンド | 例 | 内容 |
| --- | --- | --- |
| doctor | `gasverify doctor` | F01。環境の不足を全件列挙。`--fix`で権限を広げない下準備のみ自動実施 |
| push | `gasverify push` | F02。許可リストを確認してからclasp push |
| run | `gasverify run parseReceipt --args '["id"]'` | F03。devModeで実行し戻り値を出力 |
| test | `gasverify test [--filter parse]` | F04。setup→test\_\*→teardownを実行し集計 |
| verify | `gasverify verify` | push→testを一括実行。Claude Codeからは原則これだけを呼ぶ |

全コマンドが`--profile personal|work`を受け付ける。省略時は設定ファイルの既定値を使う。認証の期限切れ（personalでは最长7日）は終了コード2とし、再ログイン手順を案内する。

**9.2 終了コード（F05）**

| コード | 意味 | AIの次の行動 |
| --- | --- | --- |
| 0 | 全テスト成功 | 完了報告 |
| 1 | コードの誤り（例外、期待値不一致、実行時間超過） | 診断書の箇所を修正してverifyを再実行 |
| 2 | 準備不足（API未有効、デプロイなし、スコープ不足、許可リスト外） | コードは触らず、doctor --fix または人への依頼 |
| 3 | 実行基盤障害（通信エラー、Google側の一時障害、クォータ） | 時間を置いて再実行。繰り返す場合は人へ報告 |

コード3はgasrunにない本設計独自の区分。「コードを直しても解決しないこと」をAIに知らせ、不要な修正を防ぐ。

**9.3 原因分類の判定ルール（2026-11-03 実測に基づく）**

| 応答 | 分類 | 判定の詳細（根拠ケース） |
| --- | --- | --- |
| HTTP 200、`errorType=USER_ERROR`、メッセージに「Specified permissions are not sufficient」 | 2 | GAS内の権限不足。メッセージ内の「Required permissions」のスコープを診断書に出す（C05） |
| HTTP 200、`errorType=USER_ERROR`（上記以外） | 1 | JSの例外種別は`errorType`ではなく、`errorMessage`の先頭（`TypeError:`など）から取る（C01〜C04、L01・L02） |
| HTTP 200、`errorType=FUNCTION_NOT_FOUND` | 1または2 | ローカルにその関数があれば2（push漏れ）、なければ1（関数名の誤り）（H01） |
| HTTP 200、`errorType=USER_ERROR`、メッセージに「reading from storage. Error code NOT_FOUND」 | 2 | コードが1つもないプロジェクト（clasp create 直後など）では関数名によらずこの応答になる。未pushとして扱い、doctor --fix の自動pushにつなげる（H07、2026-11-07実測） |
| HTTP 200、正常応答 | 0 | ただし戻り値に`[native code]`を含む場合は「固有オブジェクトを返している」として1（C06） |
| HTTP 401 UNAUTHENTICATED | 2 | トークン無効。再ログインを案内（H04） |
| HTTP 403 PERMISSION\_DENIED「The caller does not have permission」 | 1または2 | 末尾が`_`の関数を呼んだ場合もこの応答になる（C10）。呼び出し前に関数名を検査し、末尾`_`なら1。それ以外は2（プロジェクト不一致やオーナー違いを案内） |
| 承認画面で403 access\_denied | 2 | テストユーザー未登録（13章の注意） |
| HTTP 500 INTERNAL backendError | 3または2 | スクリプトIDの誤りでも500が返る（H02）。呼び出し前にIDを許可リストと照合し、照合済みなら3として最大2回再試行。続く場合は2としてIDの確認を案内 |

実測で分かったその他の仕様（個人Gmail、1回の測定）：

- **行番号**：各ファイル内の行番号と一致した。入れ子では深い呼び出しから順に並ぶ。ファイル名は返らないため、ローカルの関数定義からファイルを特定する（Q7解決）
- **戻り値**：DateはISO形式の文字列、undefinedはnullとして届く。引数の文字列・数値・オブジェクトは型を保って届く
- **応答時間**：1回あたり約0.6〜2.1秒。N06（60秒以内）は十分に満たす
- **要再確認**：H03（devMode=false）とH05（マニフェストより狭いスコープのトークン）はエラーを予想したが成功した。理由は未確定のため、検証は常にdevMode=trueで行い、スコープ不足は事前検査（doctor）に頼らず実行結果（C05の型）で拾う
- **未測定**：C12（実行時間超過）、H06（Apps Script API無効時）、console.logの取得

**H03の解釈（推定）**：再デプロイしていないのにdevMode=falseで最新コードが動いた。公式リファレンスでは実行対象の指定は「API実行可能デプロイのID」とされており、スクリプトIDは常に最新コードを指す「headデプロイ」として扱われている可能性が高い。本ツールでは「スクリプトID＋devMode=true＝最新コード」だけを使い、特定の版を動かしたい場合は版付きデプロイIDを指定する。

**C12の予想（公式仕様、未測定）**：エラーの`code`は10がSCRIPT\_TIMEOUT、3がINVALID\_ARGUMENT、1がCANCELLED。C12は`code=10`で返ると予想されるため、判定表では`code=10`を1（処理量を減らす修正）とする。

**9.4 診断書（F06）**

```json
{
  "exitCode": 1,
  "category": "code_error",
  "function": "parseReceipt",
  "location": {"file": "src/receipt.js", "line": 42},
  "error": {"type": "TypeError", "message": "..."},
  "failedTests": ["test_parseReceipt_fullwidthYen"],
  "next": "src/receipt.js:42 の金額抽出で全角「￥」を扱う",
  "logs": ["..."],
  "runId": "20261103-110512"
}
```

- `location`はスタックの関数名＋行番号を、push時に保存したファイル対応表でローカルのファイル＋行に戻して作る
- `next`は分類ごとの定型文＋失敗アサーションの差分から生成。修正内容そのものはAIが考える

## 10. Claude Code連携設計

Claude Codeには「コードを変えたら必ず`gasverify verify`を通す」ことだけを守らせ、繰り返し回数と権限は設定で縛る。

| 要素 | 内容 |
| --- | --- |
| CLAUDE.md | 8章のテスト規約、9章の終了コードごとの行動ルール、副作用はラッパー経由という約束 |
| スラッシュコマンド | `/gas-verify`：verify→失敗時は診断書を読んで修正→再実行、の手順を定型化 |
| 権限設定（settings.json） | `gasverify`の実行は許可。`clasp deploy`、本番スクリプトへの`clasp push`、`appsscript.json`のスコープ変更は確認必須または拒否 |
| フック（任意） | 作業終了時にverifyを自動実行し、失敗なら終了を差し戻す。フック仕様は導入時のClaude Codeの版で確認する |

**修正ループの停止条件**

1. 終了コード0 → 完了。通ったテストと変更点を報告
2. 終了コード1が同じテストで5回続く → 停止して人に判断を仰ぐ（仕様の曖昧さを疑う）
3. 終了コード2 → `doctor --fix`を1回だけ実行。解消しなければ人への依頼事項を提示して停止
4. 終了コード3 → 待機後に最大2回再実行。解消しなければ停止

**テストの書き換え禁止**：失敗を消すために期待値を変えることは禁止。期待値を変える場合は理由を報告し、人の承認を得る。

## 10A. Webアプリ画面確認（Claude in Chrome）

Webアプリの画面と操作の流れは、Claude in Chromeでテスト用URL（末尾`/dev`）を開いて確認する。ロジックは引き続きscripts.runのテスト関数で確認し、画面確認は表示と操作の流れ（E2E）に絞る。

**前提**

- `/dev`のURLはスクリプトの編集権限を持つユーザーだけが開け、常に最新の保存コードで動く。push後の再デプロイは不要
- 業務環境では公開範囲を「全員」にできないが、本人のChromeでログイン状態のまま開くため影響しない
- GASのHTMLサービスはiframeで隔離されている。iframe内のコンソールと画面要素を読み取れるかは未検証（Q9）

**手順**

1. `gasverify verify`（ロジックのテスト）を先に通す
2. `gasverify.config.json`に登録した`/dev`のURLを、Claude in Chromeの新しいタブで開く
3. シナリオファイル（`test/e2e/*.md`）の手順どおりに操作し、各手順でスクリーンショットを取る
4. 画面表示・コンソールログ・通信内容を読み取り、シナリオの期待結果と照合する。サーバー側のログはclasp logsで補う
5. 不一致ならコードを修正→push→2へ戻る。同じシナリオで3回失敗したら停止して人へ報告
6. 合格したら操作をGIFで保存し、受け入れ試験の証跡にする

**Webアプリ側の実装規約**

| 規約 | 理由 |
| --- | --- |
| `google.script.run`には必ず`withFailureHandler`を付け、`console.error`と画面のエラー欄に出す | サーバー側の例外は、何もしなければ画面に出ないため |
| 操作対象の主要要素に`data-testid`を付ける | 画面変更で操作が壊れにくくするため |
| 処理の完了・失敗を画面上の文言で表示する（例：「保存しました」） | コンソールを読めない場合（Q9）でも、スクリーンショットで合否を判定できるようにするため |
| `/dev`でも`TEST_MODE`とテスト用シートを使う | `/dev`は最新コードが本物の権限で動くため |

**シナリオファイルの例**

```markdown
# 購入依頼の登録
前提: setup_e2e を実行済み（テスト用シートを初期化）
1. data-testid=item-name に「テスト品目A」を入力
2. data-testid=amount に「1200」を入力
3. data-testid=submit を押す
期待: 「保存しました」が表示され、コンソールにerrorがない
後確認: gasverify run e2e_checkLastRow で最終行が「テスト品目A, 1200」
```

画面操作の後、書き込まれたデータはscripts.runの関数で確かめる。画面とデータの両方で合否を判定するためである。

**安全面**

- Claude in Chromeは本人のログインで動くため、操作できる範囲は本人の権限と同じ。シナリオにないサイトやタブは操作しない
- 本番のデプロイURL（末尾`/exec`）は操作対象外
- 送信・削除など取り消せない操作は、シナリオで指定したテストデータに対してのみ行う

* Chromeは個人用と会社用でプロファイルを分け、確認対象のアカウントでログインしているプロファイルでのみ操作する。複数プロファイルでのClaude in Chromeの扱いはPoCで確認する

## 11. セキュリティ・権限設計

AIが自動で行えるのは「検証用スクリプトへのコード反映と実行」まで。権限を広げる操作と本番への反映は、すべて人が行う。

| 操作 | AI単独 | 人の承認 |
| --- | --- | --- |
| 検証用へのpush、関数実行、テスト | 可 | 不要 |
| API実行可能デプロイの作成（検証用のみ） | 可 | 不要 |
| Cloud側のAPI有効化 | 不可 | 必要（初回のみ） |
| OAuthスコープの追加・再承認 | 不可 | 必要 |
| 本番スクリプトへのpush・デプロイ | 不可 | 必要（対象外・手動） |
| テストモード解除での実メール送信 | 不可 | 必要 |

- **認証情報**：OAuthクライアントは社内管理の標準Cloudプロジェクトで発行。トークンはユーザーホーム配下に保存し、リポジトリに含めない
- **スコープ**：ツールのトークンは検証対象スクリプトのマニフェストに必要な分だけを要求。`doctor`が差分を示し、広いスコープより狭いスコープでの書き方を先に提案する（例：`drive`より`drive.file`）
- **実行者**：devModeはオーナーのみのため、検証用スクリプトのオーナーは開発者本人とする。共有ドライブ配下での扱いは要確認（Q6）
- **外注先との関係**：外注納品物のGASを検証する場合も、自社アカウント所有の検証用コピーに対してのみ実行する

**自宅PC・2アカウント運用での追加ルール**

- 認証情報はプロファイルごとに別フォルダへ保存し、取り違えを防ぐため実行時にアカウントのメールアドレスを必ず表示する
- 許可リストはプロファイルごと。workのスクリプトIDをpersonalの認証で操作しようとした場合は拒否する（終了コード2）
- 自宅PCの紛失・共用に備え、workの認証情報は作業終了後に破棄できるよう`gasverify logout --profile work`を用意する
